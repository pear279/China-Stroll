# 本地 Supabase 迁移与回滚验证设计

## 目标

为 China Stroll 建立可重复使用的本地 Supabase 数据库环境，从空库应用仓库中的全部迁移和种子数据，执行两套 SQL 回滚测试，并证明数据库可以再次从空库完整重建。

本子项目只验证本地数据库。它不连接远程 Supabase 项目、不运行 `supabase db push`，也不把新增迁移应用到线上。

## 现状

- 仓库已有 `supabase/config.toml`，本地数据库版本设为 PostgreSQL 17。
- 仓库已有按时间排序的迁移、`supabase/seed.sql` 和两套事务型 SQL 测试。
- SQL 测试分别覆盖业务表权限与 RLS，以及行程命令的权限、幂等、版本冲突、地点审核门槛和新增日期行为。
- 本机已安装 OrbStack，但当前未运行。
- 本机有 Docker 客户端，但当前没有可用的 Docker 引擎。
- 本机尚未安装 Supabase CLI。

## 方案选择

采用现有 OrbStack 作为容器运行时，通过 Homebrew 安装 Supabase CLI。该方案与 Supabase 的本地开发流程一致，能保留稳定的本地服务和固定端口，也便于后续开发者重复运行。

不采用 `npx supabase` 作为主入口，因为它会把每次执行与 npm 下载和版本解析绑定。也不在远程 Supabase 项目上执行验证，因为迁移试跑和事务测试不应与线上状态混合。

## 执行流程

### 1. 环境准备

启动 OrbStack，并等待 `docker info` 成功返回服务端版本。随后通过 Homebrew 安装 Supabase CLI，记录实际安装版本。

环境准备只修改本机开发工具，不修改远程数据库。若 OrbStack 无法启动或端口 `54320` 至 `54324` 被占用，停止后报告具体冲突，不改动仓库端口规避未知服务。

### 2. 首次干净重建

在仓库根目录启动 Supabase 本地服务。执行 `supabase db reset`，由 CLI 创建空数据库、按文件名顺序应用 `supabase/migrations` 下的全部迁移，并加载 `supabase/seed.sql`。

重建失败时保留原始错误信息，定位到具体迁移或种子语句。不得跳过失败迁移，也不得手工修改本地数据库使测试继续。

### 3. SQL 回滚测试

使用 Supabase 本地 PostgreSQL 容器内自带的 `psql` 连接 `postgres` 数据库，依次运行：

1. `supabase/tests/mvp_business_schema.sql`
2. `supabase/tests/mvp_trip_commands.sql`

调用必须启用 `ON_ERROR_STOP=1`，任何 SQL 异常都使命令立即失败。两个测试文件各自在事务中创建测试资料并以 `rollback` 结束，因此成功后不保留测试用户、旅行、地点或命令记录。

测试后查询固定测试 UUID 和 `command-test-draft-place`，确认相关测试数据均不存在。该残留检查独立于测试文件本身，避免因提前结束或脚本回归而误判成功。

### 4. 第二次干净重建

SQL 测试通过后再次执行 `supabase db reset`。第二次重建用于证明迁移与种子不依赖第一次执行留下的隐式状态。随后运行轻量完整性检查，确认核心表、命令函数和种子地点存在。

### 5. 可重复入口与记录

在仓库中增加一个本地数据库验证脚本，并通过 `package.json` 暴露单一命令。脚本负责：

- 检查 `supabase` 和 `docker` 是否可用；
- 确认 Docker 引擎在线；
- 执行干净重建；
- 在 Supabase 数据库容器中运行两套 SQL 测试；
- 检查测试数据没有残留；
- 再次干净重建并执行完整性检查。

脚本不得安装软件、启动桌面应用或连接远程项目。环境安装和 OrbStack 启动只在首次人工准备阶段完成，这样 CI 或其他开发者运行验证时不会发生隐式系统变更。

更新开发记录，写明本地工具版本、执行命令、验证结果，以及线上迁移仍未应用。

## 错误处理

- OrbStack 未启动：停止并提示启动容器引擎。
- Supabase CLI 缺失：停止并给出 Homebrew 安装命令。
- 端口冲突：报告占用端口和进程，不自动终止其他服务。
- 迁移或种子失败：报告首个失败文件和数据库错误，不继续 SQL 测试。
- SQL 测试失败：保留失败测试名称和错误详情，不执行成功结论。
- 测试数据残留：即使 SQL 文件没有报错，整体验证仍失败。
- 第二次重建失败：整体验证失败，说明迁移链不可重复。

## 验收标准

本子项目必须同时满足以下条件：

1. OrbStack 提供可用的 Docker 引擎，Supabase 本地服务全部健康。
2. PostgreSQL 17 空库能够应用全部迁移和 `seed.sql`。
3. 两套 SQL 测试均以零退出码完成。
4. 权限、RLS、幂等、版本冲突、地点审核门槛和新增日期断言全部通过。
5. 测试固定 UUID、临时地点和测试旅行没有残留。
6. 第二次 `supabase db reset` 成功。
7. 核心业务表、命令函数和种子地点在第二次重建后存在。
8. 可通过仓库中的单一命令重复执行完整验证。
9. 没有连接或修改远程 Supabase 项目。

## 非目标

- 不修复 SQL 测试发现的业务缺陷；若发现缺陷，先报告并为后续修复单独设计。
- 不审核首批 20 个景点资料。
- 不生成人工智能检索向量。
- 不开发行程编辑或地图功能。
- 不选择或配置正式底图。
