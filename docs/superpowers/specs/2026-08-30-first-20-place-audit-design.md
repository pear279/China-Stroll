# 首批 20 个景点审核与本地数据发布设计

## 目标

从仓库现有 52 个北京地点中选定首批 20 个，完成可追溯的 WGS84 展示坐标、地址、开放时间、票务、预约和入口资料审核，并把基础地点、中英文本地化、来源和结构化游览信息纳入可重复执行的本地 Supabase 迁移。

完成后，干净的 PostgreSQL 17 本地数据库无需依赖线上项目已有数据，即可通过公开地点接口读取这 20 个已审核地点。线上 Supabase 不在本子项目范围内，不运行 `supabase link` 或 `supabase db push`。

## 资料边界

`references/` 和 `data/` 是本轮的起始材料。

- `data/50景点信息sql表 .csv` 提供 52 个候选地点的中文内容和现有坐标。
- `data/coordinate-reviews.json` 提供故宫、景山和天坛三处已复核坐标。
- `data/processed/places.zh-CN.json`、`guide_segments.zh-CN.json` 和 `review-seed.sql` 是此前生成结果，只用于交叉检查，不作为新的唯一事实源。
- `references/景点来源与图片审核.md`、`景点数据与AI检索方案.md`、`MVP数据结构与接口契约.md`、`开发规划.md` 和 `迭代版.md` 规定审核标准、字段含义和发布门槛。

仓库材料中的动态事实可能已经过期。开放时间、票价、预约规则、入口和地址必须重新检查景区官网、北京市政府、主管单位或其他第一方页面。无法从可靠来源确认的字段不得推断。

## 数据架构

### 审核资料包

新增受版本控制的 JSON 资料包，作为本轮事实的唯一仓库来源。资料包按地点保存：

- 稳定字段：地点标识、类别、推荐时长；
- 展示坐标：纬度、经度、坐标系、OSM 对象编号、OSM URL、复核时间；
- `zh-CN` 与 `en` 本地化内容：名称、别名、标签、简介、历史、看点、游览提示、实用说明和拍照提示；
- `zh-CN` 与 `en` 游览信息：地址、开放时间原文、结构化开放时间、票务说明、预约要求、预约 URL、预约说明和入口说明；
- 来源：来源键、地点、来源类型、名称、URL、事实范围、检查时间、复查时间和状态；
- 字段来源映射：坐标、地址、开放时间、票务、预约和入口分别引用哪些来源键。

来源键在资料包内唯一。中英文游览信息可以引用同一份中文官方来源，但英文内容必须是忠实摘要，不得增加来源没有支持的事实。

### 数据库存储

生成结果写入现有表：

- `places`
- `place_localizations`
- `guide_segments`
- `place_sources`
- `place_visit_information`
- `place_visit_information_sources`

不新增业务表。迁移采用幂等 upsert，目标是让干净本地数据库具备完整的首批 20 个地点。已发布内容只有在资料包明确提供同一地点和语言的新审核版本时才更新。

坐标使用景区边界或主要对象的几何中心作为地图展示点。入口文字单独写入 `entrance_notes`，不能把入口坐标替换成展示中心点，也不能把 WGS84 坐标直接传给采用 GCJ-02 的本地导航服务。

## 资料信任顺序

每项动态事实按以下优先级选择来源：

1. 景区、博物馆或运营机构官网；
2. 北京市政府、区政府或主管部门官网；
3. 官方预约平台或官方公众号公开页面；
4. 仅在缺少第一方坐标对象时使用 OpenStreetMap 作为展示坐标来源。

聚合平台、攻略、百科和搜索摘要不能单独支持开放时间、票价或预约结论。若第一方页面只给出临时公告，资料包保留公告原文的简明摘要，并提示用户出发前再次确认。

动态游览信息的 `checked_at` 使用实际检查时间，`review_due_at` 统一设为检查后 30 天。坐标复核时间独立保存，不随动态信息复查而改变。

## 校验与生成

新增一个生成脚本，提供检查模式和生成模式。

检查模式验证：

1. 名单恰好包含设计中的 20 个地点，没有重复或额外地点；
2. 每个地点有 `zh-CN` 和 `en` 两条本地化内容及游览信息；
3. 坐标位于北京合理范围，坐标系为 WGS84，并有 OSM 对象和 URL；
4. 每个动态字段都能解析到资料包中的来源；
5. 开放时间对象符合现有 `timeZone`、`weekly`、`exceptions` 契约；
6. `checked_at`、`review_due_at` 有效且复查日期不早于检查日期；
7. 票务和预约未知时使用明确说明及 `booking_required: null`，不使用猜测值；
8. URL 使用 HTTPS，只有已记录原因的来源允许 HTTP；
9. 生成结果稳定，同一资料包重复生成不会产生差异。

生成模式输出 SQL 迁移正文。迁移文件先用 `supabase migration new <name>` 创建，再由生成脚本填入，不能手工发明迁移时间戳。

## 数据流

1. 从 `references/` 和 `data/` 提取候选内容。
2. 对 20 个地点逐项检查 OSM 对象和第一方动态资料。
3. 把审核结果写入受版本控制的 JSON 资料包。
4. 运行检查模式，修正缺失、冲突、无来源或过期字段。
5. 使用 Supabase CLI 创建迁移文件。
6. 由生成脚本生成幂等 SQL。
7. 运行 `npm run db:verify`，从空库执行全部迁移、SQL 回滚测试、第二次重建和核心对象检查。
8. 使用本地公开 API 验证匿名用户只能读取已发布资料，且 20 个地点均可返回列表和详情。
9. 更新开发规划、开发记录、来源审核说明和 README。

## 错误处理

- 来源不可访问：记录检查失败，整个地点保持 `reviewed` 或 `draft`，直到替代的第一方来源通过审核；不用搜索摘要替代，也不把不完整记录设为 `published`。
- 多个第一方页面冲突：采用更新时间较新的页面，并在说明中保留冲突与复查提示。
- 没有稳定开放时间：`opening_hours.weekly` 留空，`opening_hours_text` 保存官方的动态公告说明。
- 票务未知：`ticket_notes` 明确写待确认，不填数字。
- 预约要求不明确：`booking_required` 设为 `null`，保留官方入口和复查提示。
- OSM 对象与现有坐标冲突：人工查看对象边界后再更新，不取两个坐标的平均值。
- 迁移在空库失败：不得跳过外键或手工补库，回到资料包和生成顺序修复。
- 公开读取失败：分别检查 GRANT、RLS、发布状态、本地化语言和坐标审核门槛。

## 安全与发布边界

- 所有公开表继续启用 RLS。
- 浏览器只使用 Supabase publishable key。
- 不把 service role、secret key、线上连接串或登录令牌写入资料包、日志或仓库。
- 新迁移只在本地数据库执行，本子项目不修改线上 Supabase。
- 新地点只有在内容、坐标和游览信息都完成审核后才设为 `published`。
- 生成脚本不能连接数据库或网络；它只读取本地资料包并生成确定性 SQL。

## 验收标准

1. 资料包只包含并完整覆盖确认的 20 个地点。
2. 20 个地点都有 WGS84 展示坐标、OSM 对象、复核时间和可追溯 URL。
3. 20 个地点都有中英文地址、开放时间、票务、预约和入口说明。
4. 每条动态信息至少关联一条审核来源。
5. 20 个地点能在干净本地数据库中发布，匿名列表和详情读取成功。
6. 未完成坐标或发布审核的其他地点不会出现在公开列表。
7. `npm run db:verify` 连续完成两次空库重建和两套 SQL 回滚测试。
8. 类型检查、代码检查、51 项现有自动测试和三类生产构建通过。
9. 资料包校验和 SQL 生成是确定性的。
10. 没有连接或修改线上 Supabase 项目。

## 非目标

- 不拆分故宫、天坛等大型地点的内部展项。
- 不生成检索向量。
- 不开发行程地点编辑。
- 不选择正式底图或道路路线服务。
- 不把迁移应用到线上。
- 不设计位置共享。
