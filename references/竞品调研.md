# AI 旅游导览竞品与技术方案简报

观察日期为 2026 年 8 月 26 日。我核对了产品官网、公司披露、应用商店、GitHub 源码和官方定价。未采用论坛、短视频和厂商无法证明的市场数据。

## 一　成熟商业产品

### 国内　携程旅行

1. 市场与用户

携程集团 2025 年净收入 624 亿元，同比增长 17%，全年服务约 2000 万入境游客。该数据属于集团口径，不能视为携程旅行单一应用数据。核心用户习惯在手机内完成查询、规划、预订和售后。[携程 2025 年业绩](https://investors.trip.com/news-releases/news-release-details/tripcom-group-limited-reports-unaudited-fourth-quarter-and-5)

2. 核心功能

AI 行程助手会结合目的地、天数和旅行偏好生成计划，核对开放时间、游玩时长与交通时间。用户可以在地图上拖动调整，并继续进入酒店、交通和活动预订。[携程 AI 行程助手](https://www.ctrip.com/tripplanner)

3. 技术判断

携程公开材料能确认其使用自有旅游库存、实时数据、推荐排序和 AI 助手。具体服务架构没有公开。合理实现方式是让模型调用地点、交通、库存和订单工具，输出带操作入口的结构化卡片。

4. 对 China Stroll 的启发

借鉴可信数据与可执行建议。为地点资料保存来源和更新时间，AI 只提出日程改动。门票和酒店第一版使用外部跳转，暂不建设预订系统和人工定制服务。

### 海外　Wanderlog

1. 市场与用户

Google Play 显示 Wanderlog 超过 100 万次下载，评分 4.7，约 3.4 万条评价。主要用户包括自由行规划者、家庭和朋友团体，以及需要详细路线的公路旅行者。[Google Play](https://play.google.com/store/apps/details?id=com.wanderlog.android)

2. 核心功能

地图与每日行程同时展示同一批地点，支持拖动排序、路线计算、预约邮件导入、共同编辑、费用分摊和离线访问。[Wanderlog 功能页](https://wanderlog.com/plan-a-trip)

3. 技术实现

官方招聘页披露其网页使用 React，移动端使用 React Native，服务端使用 Node.js 和 Express。团队还维护网页数据采集、预约邮件解析和 LLM 处理流程，并逐步使用 Docker 与 Kubernetes。[Wanderlog 技术说明](https://wanderlog.com/blog/jobs/full-stack-engineer/)

4. 对 China Stroll 的启发

直接借鉴地图与日程共用地点数据、查看与编辑权限、轻量离线行程。预约自动导入先采用上传、解析预览、用户确认三步流程，避免错误内容直接写入日程。

## 二　GitHub 开源项目

### OpenTrip

1. 设计思路

一次旅行对应一个共享空间。地图、日程、预约、费用、成员讨论和 AI 建议都属于这次旅行。

2. 功能与技术

项目使用 React、Vite、Hono、PostgreSQL、MapLibre 和 Vercel AI SDK，可部署到 Cloudflare 或 Docker。AI 写操作需要用户确认，并绑定旅行版本。[OpenTrip](https://github.com/stvlynn/OpenTrip)

3. 可借鉴实现

为 `trips` 增加版本号，为 AI 建议保存生成时的版本和结构化操作。用户确认时，服务端检查权限与版本。版本不一致就重新生成建议。

OpenTrip 采用 Apache 2.0，适合参考和复用。项目公开使用规模较小，不能把仓库完整度当成线上运行证明。

### TREK

1. 设计思路

TREK 强调自托管、单容器、离线使用和可选功能模块。用户可以先使用基础行程，再按需启用预算、文档、协作和 MCP。

2. 功能与技术

项目使用 React、Vite、NestJS、SQLite、WebSocket、Workbox 和 Dexie。一个 Docker 容器即可运行，数据保存在 SQLite 文件和上传目录。[TREK](https://github.com/liketrek/TREK)

离线数据按用户保存到 IndexedDB。离线写操作进入队列，并附带幂等标识和修改时间。服务端发现冲突后返回 409，再让用户选择保留哪一版。[TREK 离线方案](https://github.com/liketrek/TREK/wiki/Offline-Mode-and-PWA)

3. 可借鉴实现

第一版缓存当天行程、重点地点文字和紧急信息。离线修改先进入本地队列，联网后按顺序提交。AI 建议和普通行程修改共用版本检查。

TREK 使用 AGPL 3.0。直接复制代码到商业服务前需要确认开源义务。150 多个 MCP 工具、复杂后台和大量附加模块不适合第一版。

## 三　轻量技术方案

### 方案一　最快上线

采用 React、Vite 和 PWA，前端放 Cloudflare Pages。Supabase 提供 PostgreSQL、登录、文件和实时通知。一个 Cloudflare Worker 负责 AI、地图服务转接和权限检查。

Supabase 正式方案从每月 25 美元起，包含备份和一定用量。开发速度最快，适合当前关系数据和共同日程。[Supabase 定价](https://supabase.com/pricing)

缺点是依赖两个托管平台。必须在北京真机测试网络。如果核心接口五分钟测试中多次失败，或正常请求的高位响应时间超过两秒，应改用更靠近用户的部署区域。

### 方案二　最低平台费用

采用 Cloudflare Workers、D1、R2 和静态 PWA。付费 Workers 每月最低 5 美元，R2 提供 10 GB 免费存储额度。[Workers 定价](https://developers.cloudflare.com/workers/platform/pricing/) [R2 定价](https://developers.cloudflare.com/r2/pricing/)

优点是服务少、部署统一、费用低。缺点是登录、实时通知和数据管理需要自己多写一些代码。多人同时编辑频繁出现版本冲突时，应迁移到 PostgreSQL 和成熟实时服务。

### 方案三　封闭测试最省事

参考 TREK，使用一个 Docker 容器、SQLite 和本地文件目录。租一台小型服务器即可运行。

它适合几十组种子用户和内部演示。需要自己处理备份、更新、HTTPS 和故障恢复。产品开始承担公开用户的全天可用要求后，应迁移到托管数据库和对象存储。

## 四　推荐选择

优先采用方案一。它最符合易开发、易上线和少运维的要求。

第一个开发切片只做一条完整过程。

1. 创建北京旅行。
2. 加入三个精选地点。
3. 在地图和日程中看到相同地点。
4. 打开一段可信导览。
5. 使用接下来去哪。
6. 确认 AI 建议后更新共同日程。

验收时检查两名成员看到相同结果，断网后仍能查看当天行程，AI 未经确认无法写入，旧版本建议会被拒绝。

地图公开展示需要单独检查合规要求。自然资源部和工信部门要求公开地图注明来源与审图号，互联网地图服务还涉及地图审核和备案。第一版宜接入有资质的中国地图供应商，并在上线前完成专项确认。[地图使用规范](https://hnca.miit.gov.cn/zwgk/tzgg/tz/art/2024/art_270c90866b994bb69a020ce812de6278.html)
